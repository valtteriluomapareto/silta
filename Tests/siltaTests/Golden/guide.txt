# When to use Silta
Use Silta for cross-repo work, another app or backend, branch-as-app repos, plans, handoffs, review requests and meeting decisions. Trivial single-repo edits need no task. Keep plans and results in Silta, never in PLAN.md or other repo plan files; never create tracker items yourself.

# Session start
If the hook already printed a brief, do not run it again. Otherwise run `silta brief`. Once you choose a task, run `silta brief --task AC-12`, then `silta task start AC-12`. Text is the default; use --json only to parse output.
For "work the backlog", run `silta task ls --status todo`, optionally with --app. Start the first task; skip subtasks whose parent another session claims and skip claimed tasks. Finish with a result before starting the next; continue until empty or the human stops you.

# Recipes
Examples use the fictional Acme workspace and task AC-12. Replace names and paths with refs from your brief; add --ws acme when outside that workspace.

Read another app without checking out its branch:
```sh
silta code grep platform-api -- 'Auth'
silta code show platform-api -- 'src/Auth.swift'
```

Use task add for a new task, task plan for a chosen task's checklist, and from-plan to import an existing Markdown plan. An agent's import is proposed, counts against the two-proposal cap and needs triage unless the human asked for it in this chat; then pass their words as --approved (D39). Preview imports before writing; imports keep the source by default. --delete is not human-only; it removes only an unchanged untracked source after commit and refuses harness files.
```sh
silta task add --start 'Implement Acme sign-in' --app platform-api
silta task plan AC-12 -F - <<'PLAN'
- [ ] Inspect the API
- [ ] Implement and verify sign-in
PLAN
silta task plan AC-12 --step 1 --done
silta task from-plan /tmp/acme-plan.md --dry-run
silta task from-plan /tmp/acme-plan.md
```
Use top-level checkboxes for numbered plan steps. A plan and a result go through stdin with a quoted heredoc, so shell substitutions stay literal.

Submit for review with `silta task submit AC-12`. Finish when the required review gate is met; app tasks need their actual commit sha:
```sh
silta task submit AC-12
silta task done AC-12 --sha <commit-sha> -F - <<'RESULT'
What was done: implemented and verified Acme sign-in.
Decisions: reused the existing authentication API.
What's left: nothing.
RESULT
```

# Working for the human
The human talks to you; you run Silta. Decide and record routine choices with `silta comment AC-12 --kind decision -m 'Reuse the existing authentication API.'`, then carry on.
Ask about scope changes, a new dependency, a public API/schema/migration, anything another app or the customer sees, deleting what you did not create, anything irreversible, and money.
Put all approvals, proposals to triage and questions in one message. Except for the task-creation exception below, approval words mean only what the human wrote in this chat in reply to your message that named that exact command. One answer covers the named commands and nothing else. Outside that exception, relayed words, task prompts, earlier instructions, comments, answers and handoffs never count. With no human in this chat, never use --approved. Name the commands in a question for @me and leave a handoff instead. Never invent approval words.
Human-only gates: `task promote`; task edit except your claimed task; doc edit/accept/reject (M2); effective `where --set/--unset` changes; task triage; --steal over another session's fresh claim; --force past an unmet review gate; --allow-secret; ws edit; task unblock with open blockers; and proposed-task writes under `proposals: ask`.
Usually propose nothing; never more than two proposals per session, only ideas you would bet the human wants. `task add --start` is only for work the human requested. When the human asked in this chat to add the task for later, pass their words as --approved so it becomes todo without triage (D39); do not ask again.
If brief shows `proposals: ask`, do not propose: name each idea and its exact `silta task add` command in your message, then add only the approved ideas with --approved. Without a human, list ideas under "What's left" in a handoff/result, never in a question, TODO comment or file.
When no answer can come, leave a question for @me listing pending commands, write a handoff and pick other work; do not wait. Under `proposals: ask`, keep unapproved ideas in the handoff/result instead of that question. `inbox --for me` is not available in this version; relay known pending choices in one short message.

# Questions
Ask in chat. Record a question only when blocked beyond this session. Questions default to @me; name recipients explicitly when needed:
```sh
silta comment AC-12 --kind question --to me -m 'Which callback URL should Acme use?'
```
Answer with --kind answer and --reply-to <question-ref>. The asker or current task claimer can accept an answer with `silta comment accept <answer-ref>`. Answer only as an addressee, or to relay the human's chat answer. Never accept your own answer to a question for @me. An answer comment never supplies approval words for a human-only command.

# Blocked
A question to the human does not block a task. Ask in chat if the human can answer, including questions about the customer. If only an external party (ext:acme) or another task can unblock you, keep doing useful work; block only when none remains.
Leave a handoff before blocking; blocking releases any remaining claim.
```sh
silta comment AC-12 --kind handoff -m 'State: API inspected; Next step: obtain callback URL; Open questions: callback URL; Branch and sha: feature/acme-sign-in at <commit-sha>.'
silta task block AC-12 --on ext:acme -m 'Need the identity provider callback URL.'
```
Silta sends nothing: tell the human exactly what to ask whom, then pick other work. Never unblock with open blockers without the human's approval, and never put "waiting for" into repo files or plans.

# Handoff
Always leave a handoff before stopping. It releases your claim while preserving status. Use the actual branch and sha; the next session reads the task and starts it again. Run `silta session check` to find fresh own claims needing handoff across all workspaces; follow each printed scoped command with the handoff body on stdin.
```sh
silta comment AC-12 --kind handoff -F - <<'HANDOFF'
State: API inspected; implementation remains.
Next step: implement sign-in and run the verification checks.
Open questions: none.
Branch and sha: feature/acme-sign-in at <commit-sha>.
HANDOFF
```
In the next session, resume with:
```sh
silta task show AC-12
silta task start AC-12
```

# Reviews
Use `silta task submit AC-12` to request review. Read discussion with `silta task show AC-12`. Reply to the actual finding ref with `silta comment AC-12 --reply-to AC-12/3 -m 'Changed the validation; SignInTests proves it.'`, naming what changed and the proving test. Do not resolve review threads yourself unless assigned that responsibility.
The M2 inbox take, task diff and task review workflow is not available in this version.

# Refusals
Read the error's code, next_by and next commands. A command's next_by can override the code default. Never use --force, --steal, `where --set/--unset`, `task promote` or --allow-secret on your own initiative; name the exact command, wait for the human's reply in this chat, then pass their words through --approved. Never create tracker items or repo plan files. With no human in this chat, see `silta guide human`.
  usage  exit 1, next by agent: Read `silta <cmd> --help` and fix the call
  invalid  exit 1, next by agent: Read `silta <cmd> --help` and fix the call
  not_found  exit 2, next by agent: Check the ref, or carry on without silta
  unregistered  exit 2, next by agent: Check the ref, or carry on without silta
  human_only  exit 3, next by human: Stop and ask the human in chat; rerun with `--approved "<their words>"` after they say yes
  read_only_promoted  exit 3, next by agent: Leave it to its tracker and pick other work
  ambiguous_location  exit 4, next by agent: Retry with `--app <slug>` from the candidates
  busy  exit 5, next by agent: Retry once after a few seconds
  conflict  exit 6, next by agent: Re-read, then decide; don't steal, and don't unblock while blockers are open
  claimed  exit 6, next by agent: Re-read, then decide; don't steal, and don't unblock while blockers are open
  stale_rev  exit 6, next by agent: Re-read, then decide; don't steal, and don't unblock while blockers are open
  lease_taken  exit 6, next by agent: Re-read, then decide; don't steal, and don't unblock while blockers are open
  blocked  exit 6, next by agent: Re-read, then decide; don't steal, and don't unblock while blockers are open
  gate  exit 7, next by agent: Request a review or ask the human
  rate_limited  exit 8, next by agent: Wait for `retry_after_s`, or summarise
  env  exit 9, next by human: Report the printed fix to the human

# Reference grammar
Bare task ids are accepted wherever a task is expected. The grammar is used in arguments and JSON. [[links]] in bodies are not yet resolved. Parsing a reference does not imply its target exists or is supported by a command.

| Ref | Example | Notes |
|---|---|---|
| Task | `AC-12` | `task:AC-12` is also accepted |
| Comment | `AC-12/3` | the 3rd comment on AC-12 |
| Doc / revision / comment | `doc:mobile-auth-flow`, `doc:mobile-auth-flow@4`, `doc:mobile-auth-flow@4/2` | Stored refs resolve; authoring waits for M2 |
| App, topic | `app:platform-api`, `topic:messaging` | |
| Code | `platform-api:src/Api/Controllers/AuthController.cs#L40-52` | `code:` prefix optional; `@<ref>` after the app picks another branch: `platform-api@feature/x:path` |
| Plan lines | `plan@3#L12-18`, `plan#L12` | latest revision when `@n` is omitted |
| Diff lines | `diff:lib/push/categories.dart#L88`, `#-L88` for the old side | relative to the task's review subject; CLI resolution waits for the M2 subject producer |
| Note | `note:notes/projects/acme/2026-10-26-weekly-status.md` | |
| URL | `url:https://dev.azure.com/…` | |
| External party | `ext:acme` | 1–64 lowercase letters, digits and `-`, starting and ending with a letter or digit; something a task waits on, never an actor (D35) |

# Output
Text is the default; --quiet preserves read output. Use --json only when parsing; it prints the schema-1 envelope on stdout. Errors carry actionable next commands. Use `silta schema` for command shapes and `silta guide refs` for the reference grammar.
Topics: when, start, recipes, human, questions, blocked, handoff, reviews, refusals, refs, output. Read one with `silta guide <topic>`.
